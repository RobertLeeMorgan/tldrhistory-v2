# New application onboarding

Use this checklist for each independently deployed application. The infrastructure owner reviews fixed configuration; the application repository owns code, tests, images and migrations. No application is provisioned merely by following this document.

1. **Contract and capacity.** Record app name, GitHub repository/owner, intended domains, frontend/backend/worker services, health responses, image repositories, CPU/RAM/disk budget, shutdown behavior and persistent data. Inspect host headroom and restore workspace before allocation. Keep Redis disabled unless the app has a defined cache/queue need.
2. **Images and Actions.** In the application repository, test on pull requests without deployment credentials. On protected `main`, build linux/amd64 images, publish to GHCR with that workflow's `GITHUB_TOKEN` (`contents: read`, `packages: write`), capture immutable digests and use `concurrency` with `cancel-in-progress: false`. Pin third-party actions. The VPS's `read:packages` PAT is for private image pulls only; do not copy it into Actions. Link each private package to its repository and grant the required read access.
3. **Reviewed Compose and runtime configuration.** Install `apps/<app>/compose.yaml` in the root-owned infrastructure checkout. Pin images by supplied digest variables; no app-published host ports, Docker socket, privileged mode or startup migrations. Configure user, caps, filesystem mounts, healthcheck, limits, stop grace and bounded logs. Store app environment/secret files in root-controlled `/etc/vps-infra/apps/<app>/`; document the required container UID access. Register every persistent host path or volume and its backup consistency rule.
4. **Networks and Caddy.** Create a per-app proxy bridge and, if the app needs PostgreSQL, a per-app internal database network. Attach Caddy only to the proxy network and PostgreSQL only to the app's database network through reviewed infrastructure changes. Validate Caddy routing before reload. Arrange domain/DNS changes separately; verify trusted HTTPS, upstream response and both configured IP families. Retain the existing infrastructure health endpoint.
5. **PostgreSQL.** Use the one shared server. Provision an empty distinct database and runtime/migrator roles using the reviewed SQL procedure. Set passwords interactively, grant only necessary privileges, bound connection pools and verify cross-app denial. Register the new database in `BACKUP_DATABASES`, then take a current offsite backup before applying production schema changes. Migrations are separately reviewed and never run at PostgreSQL startup.
6. **Backup and monitoring.** Add persistent files to `/etc/vps-infra/backups/paths.txt`; verify each source exists and can be restored consistently. Run a backup, verify the B2 snapshot and restore the app data into an isolated target. Add every long-running Compose service to `MONITOR_SERVICES` and configure external HTTPS/TLS monitoring of an application-level readiness URL. Check alert routing and backup freshness after deployment.
7. **Restricted deployment access.** Create one dedicated SSH identity/account for this app, outside the Docker group. Install an administrator-owned `deploy/<app>.conf` policy and exact app Compose file. Bind the public key to `vps-ssh-command <app>` with the reviewed `authorized_keys` restrictions and a narrowly scoped `sudoers` rule for only `/usr/local/sbin/vps-deploy <app> ...`. Keep the private key in the application repository's protected deployment secret/environment. Pin the VPS host key in Actions. Test denied shell/other-app access before the first release.
8. **Release and recovery.** Deploy only reviewed immutable digests through the forced command. Verify every component's Docker health and an uncached external readiness response; record current/previous releases. Exercise a failed release and explicit `recover`, then `rollback` to a compatible prior image. A rollback does not reverse database migrations or external side effects. Re-check backups, monitoring, port bindings and resource usage after release.

Follow [the application contract](deployment-contract.md), [PostgreSQL procedure](../services/postgres/README.md), [deployment access](ci-cd.md), [operations](operations.md) and [disaster recovery](disaster-recovery.md). Changes to DNS, production data or a live application's traffic require their own authorisation.
